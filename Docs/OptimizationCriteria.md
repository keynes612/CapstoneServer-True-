# 서버 최적화 판정 기준

## 세 줄 요약

1. **비교:** 모두에게 다 보내는 기본 방식(P0)과 최적화한 방식을 같은 조건에서 돌린다.
2. **성공 조건:** 서버가 보내는 데이터 양이 확실히 줄어야 한다.
3. **단, 품질은 지킨다:** 서버가 느려지거나, 클라이언트가 버벅이거나, 다른 플레이어가 늦게·틀리게 보이면 실패다.

## 판정 기준

| 항목 | 기준 |
|---|---|
| P0 (기본) | 같은 구역 전원에게 1초에 20번 전체 위치 전송 |
| P1 (현재 NetLOD) | 가까우면 자주, 멀면 가끔, 40m 밖은 안 보냄 (나갈 때 "사라짐" 메시지 전송) |
| 주 지표 | 서버 → 클라이언트 **실제 네트워크 사용량** (패킷 캡처로 판정, 서버 내부 추정값도 기록) |
| 서버 한도 | 틱 처리 시간(느린 쪽 5%·1%, 50ms 초과 비율)이 P0보다 나빠지면 안 됨 |
| 클라이언트 한도 | 프레임 시간이 느린 쪽 5% 기준 16.7ms(60fps) 이하, 클라이언트당 받는 데이터가 P0보다 늘면 안 됨 |
| 품질 한도 | 가까운 상대 정보 지연 100ms 이하, 먼 상대 500ms 이하, 위치 오차 1m 이하, 유령 캐릭터·필수 상태 메시지 누락 0 |
| 실험 방법 | 봇 10 → 25 → 50 → 100명, 조건마다 5번 반복, 처음 30초 버리고 120초 측정 |

- 감소 폭이 반복 실험 사이의 흔들림보다 작으면 "개선 없음"으로 본다.
- 수치는 시작값이다. P0을 측정한 뒤 바꿀 수 있고, 바꾸면 이유를 여기에 적는다.
- 측정 기능(서버 틱·시각 기록, 클라이언트 프레임 기록, 봇, 패킷 캡처 등)은 아직 만들지 않았다.

## 필수 상태 메시지란

유저가 읽는 알림(공지·팝업)이 아니다. 서버가 클라이언트 프로그램에 "이 캐릭터를 화면에서 지워라"처럼 보내는 내부 메시지다.

| 이름 | 언제 보내나 | 안 오면 생기는 일 |
|---|---|---|
| 퇴장 | 다른 플레이어가 접속을 끊었을 때 (`S_PlayerLeft`, 있음) | 나간 사람이 화면에 멈춘 채 남음 |
| 사라짐 | 다른 플레이어가 관심 범위(40m) 밖으로 나갔을 때 (아직 없음) | 멀어진 사람이 마지막 위치에 남음 |
| 구역 이동 | 다른 플레이어가 포탈로 다른 구역에 갔을 때 (아직 없음) | 떠난 사람이 내 구역에 계속 보임 |

- 위치는 한두 번 빠져도 다음 값이 오면 맞춰지므로 덜 자주 보내도 된다.
- 필수 상태 메시지는 한 번만 빠져도 유령 캐릭터가 남으므로 줄이거나 빼지 않는다.

## 고민: 서버와 클라이언트 중 누가 일을 더 할까

| 방향 | 예시 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| 서버가 더 일함 | 받는 사람마다 거리를 계산해 필요한 것만 보냄. 위치·공격을 서버가 판정 | 데이터가 적고 치트에 강함. 클라이언트는 그리기만 함 | 인원이 늘면 서버 계산이 제곱으로 늘어남 |
| 클라이언트가 더 일함 | 서버는 덜 자주 보내고 클라이언트가 사이를 추측해 채움. 또는 다 보내고 클라이언트가 걸러냄 | 서버 계산·전송 횟수가 줄어듦 | 클라이언트 계산이 늘고, 추측이 틀리면 화면이 튐. 판정을 맡기면 치트 위험 |

### 결론: 서버 부담을 줄이고, 클라이언트에는 "가벼운 일"만 맡긴다

**클라이언트에 맡기는 것**
- 덜 자주 받은 위치 사이를 부드럽게 채우는 보간·추측 이동. 이미 `RemotePlayer`에 있고, 상대 한 명당 계산이 아주 작다.

**클라이언트에 맡기지 않는 것**
- **다 보내고 클라이언트가 거르기:** 보내는 데이터가 그대로라 주 지표가 나빠진다.
- **공격 적중·피해 판정:** 클라이언트가 결과를 조작할 수 있다.

**서버가 계속 하는 것**
- 누구에게 얼마나 자주 보낼지 정하기 (NetLOD, 이후 정책)
- 필수 상태 메시지(퇴장·사라짐·구역 이동) 보장

**이렇게 정한 이유 (현재 상황)**
- 인원이 늘면 서버 송신량과 계산이 인원의 제곱으로 늘어난다. 지금 병목이 될 곳은 서버다.
- 클라이언트는 2D 기본 도형이라 여유가 있고, 보간 기능도 이미 있다.
- 이 프로젝트의 목표는 서버 최적화이고, 주 지표도 서버 송신량이다.

**바꾸는 조건**
- 측정해 보니 클라이언트 프레임 한도를 넘거나 화면이 튀어 품질 한도를 넘으면, 서버 쪽으로 일을 되돌린다 (전송 빈도를 다시 올리는 등).
