# 서버 최적화 판정 기준

- 작성일: 2026-11-25
- 대상 코드: `KDH` 브랜치, 커밋 `af6f485` 기준의 `MyMMORPG/Server` (.NET TCP 서버)
- 상태: 판정 기준의 **틀은 확정**했다. 수치는 **시작값**이며 P0 측정 후 조정할 수 있다. 아래의 측정·코드 작업은 **아직 구현하지 않았다.**

## 1. 한 줄 요약

같은 인원·같은 움직임에서 **서버가 보낸 실제 네트워크 사용량이 기준선(P0)보다 확실히 줄고**, 그 대가로 **다른 플레이어가 보이는 품질이 정해진 선 아래로 떨어지지 않으면** "최적화 성공"으로 판정한다.

## 2. 비교 대상

| 이름 | 내용 | 현재 상태 |
|---|---|---|
| **P0 (기준선)** | 같은 구역의 **모든** 플레이어 상태를 **매 틱(20Hz)** 모두에게 전송. 관심 대상 선별 없음 | 미구현 (거리 조건을 끄는 설정으로 추가 예정) |
| **P1 (NetLOD)** | 15m 이내 20Hz, 15~40m 5Hz, 40m 밖 전송 안 함. 범위를 벗어나면 "사라짐" 알림 전송 | 거리별 전송은 구현됨. "사라짐" 알림은 미구현 |
| **P2 이후 (PQSR 등)** | 이후 결정 | 미정 |

### P0이 무거운 이유 (현재 패킷 형식으로 계산한 예시, 측정값 아님)

- 플레이어 1명 정보 = 21바이트 (ID 4 + 좌표·방향 16 + 달리기 1)
- 한 수신자가 받는 스냅샷 = 6바이트(헤더·개수) + (인원−1) × 21바이트
- 같은 구역 20명: 405B × 20명 × 20Hz ≈ **162KB/s**
- 같은 구역 100명: 2,085B × 100명 × 20Hz ≈ **4.2MB/s**
- 인원이 5배로 늘면 송신량은 약 26배가 된다. 인원의 제곱에 비례하기 때문이다.

## 3. 실험 조건 (모든 정책에 동일하게 적용)

| 항목 | 기준 |
|---|---|
| 실행 프로그램 | 같은 서버 빌드를 쓰고 정책만 설정으로 바꾼다 |
| 플레이어 | 자동 클라이언트(봇). 같은 시나리오와 같은 난수 시드 사용 |
| 인원 단계 | 10 → 25 → 50 → 100명. P0의 틱이 50ms 예산을 넘기 시작할 때까지 늘린다 |
| 측정 시간 | 시작 후 준비 구간 30초는 버리고, 120초 측정 |
| 반복 | 조건마다 5회 |
| 장비 | 같은 PC. 서버와 봇의 CPU·메모리를 따로 기록 |

## 4. 주 지표: 서버 송신량 (줄어야 함)

- **정의:** 서버가 클라이언트로 보낸 **실제 네트워크 사용량**(TCP·IP 헤더 포함)
- **단위:** 바이트/초. 서버 전체 합계와 클라이언트 1명당 값을 함께 기록
- **방향:** 서버 → 클라이언트만 평가한다. 클라이언트 → 서버는 정책과 관계없이 같다.
- **측정 방법:** 두 가지를 함께 쓴다.
  - **(기준) 패킷 캡처:** Wireshark 등으로 실제로 오간 바이트를 센다. 판정에는 이 값을 쓴다. 같은 PC 안의 통신(loopback)을 캡처하려면 Npcap loopback 지원이 필요하다.
  - **(보조) 서버 내부 추정:** 우리 메시지 바이트 + TCP 세그먼트 수 × 헤더 크기(약 40바이트). 실시간 표시와 캡처값 대조용으로 쓴다.

## 5. 보조 조건: 서버 틱 처리 시간 (나빠지면 안 됨)

- 한 틱(50ms마다 한 번)의 처리에 걸린 시간을 ms로 기록한다.
- 다음 세 값이 P0보다 나빠지면 안 된다.
  - **p95, p99:** 느린 쪽 5%, 1% 수준
  - **예산 초과율:** 50ms를 넘긴 틱의 비율

## 6. 품질 가드레일 (하나라도 넘으면 불합격)

| 가드레일 | 정의 | 한도 (시작값) |
|---|---|---|
| 상태 경과 시간 | 화면의 상대 정보가 몇 ms 전에 만들어진 것인지 | 15m 이내 p95 ≤ 100ms, 15~40m p95 ≤ 500ms |
| 표시 위치 오차 | **서버가 받은 위치**(정답)와 화면에 그려진 위치의 거리 | 15m 이내 p95 ≤ 1m |
| 유령 객체 | 갱신이 끊겼는데 화면에 남은 상대. 40m 밖으로 나가거나 구역을 옮긴 상대는 "사라짐" 알림으로 지워져야 함 | 0 |
| 필수 알림 누락 | 퇴장·사라짐·구역 이동 알림이 빠진 횟수 | 0 |

- 위치 오차 1m 한도는 달리기 속도 9m/s × 100ms ≈ 0.9m에서 정했다.
- 상태 경과 시간을 재려면 패킷에 서버 틱 번호와 시각이 필요하다. 현재는 없다.

## 7. 판정 순서

1. P0과 비교 정책을 같은 조건으로 각각 5회 실행한다.
2. **가드레일 검사:** 하나라도 넘으면 그 조건은 불합격으로 처리하고 이유를 기록한다.
3. **주 지표:** 실제 송신량이 P0보다 줄었고, 그 감소 폭이 반복 실행 사이의 흔들림보다 커야 한다. 흔들림 범위 안의 차이는 "개선 없음"으로 본다.
4. **보조 조건:** 틱 처리 시간 p95·p99와 예산 초과율이 P0보다 나빠지지 않아야 한다.
5. 인원 단계별 결과표를 작성한다. 실패·제외한 실행도 이유와 함께 모두 남긴다.

### 판정 예시 (지어낸 숫자)

| 조건 | 송신량 | 반복 간 흔들림 | 틱 p95 | 가드레일 | 판정 |
|---|---|---|---|---|---|
| P0, 50명 | 1,000KB/s | ±20 | 8ms | 통과 | 기준 |
| P1, 50명 | 400KB/s | ±15 | 7ms | 통과 | 합격 (60% 감소) |
| P1, 50명 (가정) | 400KB/s | ±15 | 7ms | 유령 객체 발생 | 불합격 |

## 8. 측정 전에 필요한 작업 (미구현, 별도 계획 필요)

- [ ] P0 정책 설정 추가 (거리 조건 끄기)
- [ ] NetLOD 범위 이탈 시 "사라짐" 알림, 구역 이동 시 기존 구역에 퇴장 알림
- [ ] 패킷에 서버 틱 번호·생성 시각 추가
- [ ] 서버 송신 바이트·세그먼트 수·틱 처리 시간 기록
- [ ] 같은 소켓에서 송신이 동시에 진행되지 않도록 정리 (현재 `SendAsync`가 겹쳐 실행될 수 있음)
- [ ] 틱 간격 정밀도 점검 (`Task.Delay`는 Windows에서 약 15ms 단위로 동작)
- [ ] 자동 클라이언트(봇)와 시나리오·시드
- [ ] 패킷 캡처 환경 (Npcap loopback)

## 9. 주의

- 한 PC에서 측정한 결과를 대규모 서비스 성능으로 일반화하지 않는다.
- 품질이 떨어진 상태로 송신량만 줄어든 결과는 개선으로 보지 않는다.
- 수치는 P0 측정 후 조정할 수 있다. 조정하면 이유와 날짜를 이 문서에 기록한다.
